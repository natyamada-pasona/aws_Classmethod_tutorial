# 7章: 優れたLambda関数を書く

## Lambdaの同時実行数（Concurrency）

- Lambda関数にリクエストが同時に来たら、その数だけ実行環境が立ち上がり並列処理される
- 1リクエスト = 1実行環境
- デフォルト上限: リージョンあたり1,000（引き上げ申請可能）
- 予約済み同時実行数（Reserved Concurrency）: 特定の関数に枠を確保 & 上限キャップにもなる
- プロビジョニングされた同時実行数（Provisioned Concurrency）: 事前に実行環境を温めてコールドスタート回避
- SQSがイベントソースの場合、Lambdaがキューをポーリング（定期的に見に行く）してメッセージを取得する方式もある

## Lambda関数のベストプラクティス

- 環境の再利用を活用する
- バックグラウンドプロセスやコールバックが完了するまで待機する
- データベースプロキシを使用してデータベース接続プーリングを管理する
  - AWSでの具体的な実装は RDS Proxy
  - Lambda → RDS Proxy → RDS/Aurora の構成で、接続プーリングを自動管理
  - コード側は接続先エンドポイントをRDS Proxyに変えるだけ
- 状態データを外部で維持する
  - Lambdaのローカル（/tmpやメモリ）に状態を保存しても、コールドスタートで消える
  - 状態はDynamoDB、ElastiCache、S3、EFSなどの外部ストアに保存する
  - 例: S3に画像アップロード → Lambdaでサムネイル生成。処理の進捗状態はDynamoDBに保存する
  - Lambdaはステートレス（状態を持たない）に徹するのが基本
- デプロイパッケージのサイズと依存関係の複雑さを最小限に抑える
  - デプロイする際、不要なライブラリ・依存パッケージを含めないこと。軽いほどコールドスタートが速くなる
- 大規模なアセットまたは共有アセット用にAmazon EFSをマウントする
  - アセット = Lambda関数が処理に使うファイルやデータ（例: 機械学習モデル、共有ライブラリなど）
  - デプロイパッケージに含めると大きくなりすぎるのでEFSに置いて読み込む
- プロビジョニングされた同時実行数を使用してコールドスタートを回避する

[AWS Lambda ベストプラクティス（公式）](https://docs.aws.amazon.com/lambda/latest/dg/best-practices.html)


#### Tips: プロビジョニングとは
「事前に準備しておく」という意味。Lambdaでは、リクエストが来る前にあらかじめ実行環境を起動して待機させておくこと。

## 環境の再利用の例: 一時キャッシュとして tmp スペースを使用

```javascript
// Node.js 16.x CommonJS AWS-SDK V2
const fs = require('fs');
const AWS = require('aws-sdk');
const s3 = new AWS.S3();

exports.handler = async (event, context) => {
    let params = { Bucket: 'myprivatebucket', Key: 'config.json' };
    let config;
    try {
        // /tmp/config.json から構成をロード
        config = fs.readFileSync('/tmp/config.json');
    }
    catch (e) {
        // S3 bucket から構成をダウンロード
        console.error(e);
        let data = await s3.getObject(params).promise();
        config = data.Body.toString('utf8');
        // write to /tmp/config.json
        fs.createWriteStream('/tmp/config.json').write(config);
    }

    return;
};
```

## 例: コールバックが完了するのを待つ

```javascript
// Callback の使用
exports.handler = function (event, context, callback) {
    ddbClient.listTables(null, callback);
};

// Async/Await の使用
exports.handler = async function (event, context) {
    const tableNames = await ddbClient.listTables().promise();
    return tableNames;
};
```

処理の完了を待たずにハンドラーが終了すると、残ったプロセスが次回の呼び出しに影響して想定外の結果になる可能性がある。そのため、callbackやasync/awaitで処理の完了を待ってからハンドラーを終了すること。
なお、Pythonなど同期的に処理する言語の場合は気にする必要はない。（とにかく全ての処理が終わってからLabmdaを閉じればいいということ。）
